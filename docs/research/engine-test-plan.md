# Engine test plan: KPIs, independent cases, and input coverage

Owner: Eli (calculation engine). Date: 2026-11-05. Status: draft for build start. Companion to `ROI.md` (formulas), `plans/03-calc-engine.md`, and `reference/roi_prototype.py`.

## Question

How do we prove the calculation engine is right, **without** testing it only against itself, and which inputs must the test set contain so every claim we make about the engine is actually checked?

## Context

- The engine is a pure TypeScript library (no I/O). It must be tested on its own before it is connected to the input form or the assistant.
- Expected outputs must come from somewhere independent of the code under test. Three sources are used, in this order of strength: **published figures** (strongest), **independent hand or spreadsheet arithmetic**, and a **second implementation** (`roi_prototype.py`; same author, so it is weaker, and it is labelled as such below).
- Our haircut bands, backing weights, floors and cost uplifts are **team judgment** (`SOURCES.md` section F). No published figure can confirm them, so they are tested as **properties and scenarios**, not as truth. This is stated in the report, not hidden.

## Sources reviewed

Every case below was opened and the numbers were recomputed independently (script outputs match to the cent or dollar). Status uses the `SOURCES.md` badges.

## Test layers (in build order)

1. **Finance layer:** pure PV, NPV, ROI (both definitions), payback functions against T1 to T6. Run first; this also pins the NPV convention.
2. **Driver layer:** each driver's gross to adjusted steps against T7 and T8.
3. **Evidence layer:** haircut, backing score, weakest link, and the gate (properties plus F3 and F4 scenarios).
4. **Project layer:** totals, scenarios, sensitivity, warnings, reconciliation.
5. **Differential layer:** generated inputs run through both the TypeScript engine and `roi_prototype.py` (needs the oracle extended to a full run).
6. **Tool layer:** wrappers with schema validation; a fake model first (offline, no API key), then one live Gemini call to prove the wiring.

The finance and driver layers test **given streams**, so the published studies (whose haircut is a flat per-row percent) can be checked without our sliding haircut. The engine therefore exposes the finance layer as its own function that takes already-adjusted benefits and costs.

## Assumptions

- Published studies are accepted as correct arithmetic; we check our engine against their tables, not their judgment.
- A 10% discount rate is Forrester's convention (stated in T1 and T2); the Green Book and NI cases use 3% and 3.5%.
- The T2 fetch result was a model-written summary of the page, so it counts as verified only because every figure re-adds exactly; the original PDF should still be opened before the final presentation cites it.

## Risks

- **Weak driver coverage:** three of four drivers have no published end-to-end case. Mitigation: formula exactness, properties, and a stated limitation in the report.
- **Circularity:** the Python oracle and the TypeScript engine share an author. Mitigation: published cases are the true check (K1 to K3); K14 is reported as second-line only.
- **Judgment parameters:** bands, weights, floors and uplifts cannot be validated by sources. Mitigation: label as team judgment on the website page and in the report, and keep them as config values.
- **Convention mismatches:** Excel's first-value timing differs from the Forrester and Sprint 4 convention. Mitigation: the finance layer states its convention and T4 tests both.

## Recommended next step

Build the finance layer and its published-case tests first (K1, K2), then the driver layer (K3), then the evidence layer and gate (K6, K7). Find two more driver-level cases (data quality and decision speed or risk) before the demo to narrow the honest gap above.
