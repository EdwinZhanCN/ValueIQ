# Structured intake integration

Project intake follows the merged step flow: `/projects/:id` collects project context/goals/uploads; `/clarify` collects numbers and evidence; `/process` uses the existing run controls. The sidebar, step bar, review and report pages belong to the merged frontend. `/workspace?view=intake` keeps the local sample/export-only editor.

Both step editors save through the authorized `/projects/:id/form` action and Zihao's conditional `saveProjectForm`. Versioned payloads are checked against the trusted server file listing. Missing essential values can be saved as an incomplete version-1 envelope, without introducing new envelope fields; invalid supplied values and foreign file references are rejected. Ready saves use the canonical serializer. Existing opaque scripted saves retain their compatibility path. Eli's PR #147 supplies strict server-side Start run validation against real project uploads; that boundary is now merged on develop. Older marked drafts remain readable for compatibility.

`shared/form.ts` owns the canonical wire schema. The engine re-exports exactly that `FormFile`; a compile-time equality assertion prevents drift. Historical engine/assistant callers use an explicitly named `LegacyFormFile` derived from the canonical definition, retaining earlier defaults and root-discount compatibility. Both validators ignore retained numeric values of unknown-tier inputs in before/after ordering. Invalid non-JSON edits retain accepted state and produce a validation issue.

Real file IDs come from project uploads; file descriptions cannot prove ownership. Numeric gap links to `/projects/:id?input=...#intake` redirect to Clarify, which reveals/focuses the question. Team-settings integration and question/answer UI remain deferred per Zihao's review. The input team does not implement engine arithmetic or new run orchestration.

Validation covers canonical fixture equality, unknown/non-JSON regressions, legacy engine compatibility and type equality, saved JSON retention, forged evidence, edit conflicts, Worker packaging and the access matrix. A real Gemini assessment still requires Eli's environment; local tests do not claim a live model result. The local sample browser-download mechanism is unchanged.
